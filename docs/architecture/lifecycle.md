# 逐集生命周期与数据一致性

`draft → open → closed → result_pending → settled / refunded`

- draft：配置 UTC 开封盘时间及角色；上一轮必须已终结，才能创建依赖其结果与继承值的下一轮正式名单。首轮例外。
- open：接受 `opens_at <= server_now < closes_at` 的订单。角色必须在本轮名单、非回忆、未在此前轮次确认死亡。允许增加合格新角色，不能删除已有订单引用的角色。
- closed：以服务端时间拒绝新订单，即使状态更新任务尚未执行。封盘原子冻结角色、开盘值、本轮订单 ID/用户/金额、总池及每角色参考值。
- result_pending：等待管理员复核；空死亡集合也需显式 result_confirmations，不能把尚未确认当“无人死亡”。死亡事实可修改但需版本比较与审计。
- settled：W>0；对每笔命中订单计算 floor(amount×P/W)，剩余整数按订单 ID 的二进制升序，每笔依次加 1。合计返还恰为 P，未命中返还 0。
- refunded：W=0，包含无人死亡、无人押中及空池；各订单原路退还，空池记录 0 金额结算但不写零值流水。

结算提交必须同时锁定/比较轮次版本，创建唯一 settlements 记录、唯一 payouts、余额更新、流水、审计和幂等响应。D1 batch 具备原子回滚，但复杂 read-modify-write 不能只靠“先读余额再写余额”；需要 SQL 条件写入或同一 Durable Object 串行化所有相关写入，且最终仍由 D1 唯一约束保证。一期的表结构并未替代这些正式服务保证。

下一轮只收录上一轮已结算/退款后的存活角色。开盘参考继承冻结时 P/S；S=0 则继承冻结的 opening_reference。新角色为 1/1。订单、押注额与池子全从 0 开始，钱包余额不清零。前台不能把“继承”解释成资金或保证返还。

正式排期不写死日期。官方页面确认日期是 2026-10-20，但具体上线时刻与逐集节奏仍需核对；如果整季同日上线，须由产品决定改为单赛季轮次，或取消继承并提前同时封盘。当前迁移只存 draft + null 时间，不自动开盘。
